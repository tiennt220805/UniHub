# Test Plan — UniHub

This file is the phase-by-phase execution schedule for `test-strategy.md`, walking `proposal.md` §15's eight delivery phases through a testing lens: what test artifact each phase must produce, and what must be true before the next phase starts. It deliberately does **not** carry a sprint calendar or a staffing table — `proposal.md` §16 states this is a single-developer delivery, so a plan built around parallel testers or sprint velocity would describe a team that doesn't exist. Phase gates, not calendar dates, are the unit of progress here.

**Out of scope, and where it actually lives:** ratios, gates, environment tiers, and the Non-Negotiable Invariant catalog (INV-01…INV-20) that apply across every phase (`test-strategy.md`); per-level tooling detail (`../test-levels/*.md`); concrete load-test scenario mechanics (`../non-functional/performance-load.md`); resilience/fault-injection scenario mechanics — circuit breaker, Redis outage, replica lag, pod kill (`../non-functional/resilience-testing.md`); adversarial security-test mechanics — JWT tampering, QR forgery, rate-limit bypass (`../non-functional/security-testing.md`); Clock-injection/short-TTL mechanics for time-based tests (`../guidelines/mocking-guidelines.md`/`../guidelines/test-data-management.md`); the actual traceability rows (`../reports/test-matrix.md`); per-phase sign-off records once a phase is actually reached (`../reports/release-sign-offs/`).

## 1. Phase-by-Phase Test Plan

**Rationale:** `proposal.md` §15 already fixes what functionality lands in each phase. This section adds, per phase, the test deliverable that phase cannot be called done without, and the concrete exit check — so "the phase is finished" has the same evidentiary bar as `test-strategy.md` §1's objectives, not just "the feature runs on my machine."

## 2. Prioritization Under Single-Developer Bandwidth

**Rationale:** `proposal.md` §16 names single-developer bandwidth as a schedule risk and already sets the mitigation: registration, payment, and concurrency correctness are the critical path; AI summarization and additional notification channels are scope delivered only after core correctness is proven. Test-writing effort follows the same order — there is no separate "testing team" to parallelize against a different priority.

**Model:** if a phase's test deliverable and a lower-priority feature's test deliverable compete for the same time, the order is:

1. The CI gate itself (stages 1–4, stood up in Phase 1 — see §1) never slips, because it's the enforcement mechanism for everything below it. Same rule for anything touching a catalogued invariant (`test-strategy.md` §2), regardless of which phase it lands in: RBAC + nightly-sync isolation (INV-01, INV-13, Phase 1); idempotency-key write, Master-routing, outbox-atomicity, payment reconciliation, circuit breaker (INV-02/03/04/05/10, Phase 2); anti-overbooking, seat-hold release, Redis fail-safe, one-instance-per-job (INV-06/07/08/09, Phase 3); consumer redelivery-idempotency, outbox-relay (INV-10/11, Phase 4); earliest-timestamp-wins reconciliation, QR/cancelled-workshop rejection (INV-12, Phase 5); S3-outage isolation (INV-19, Phase 5); audit-fail-open (INV-14, Phase 6); migration mid-rollout compatibility, self-healing, rate-limit, mesh mTLS (INV-15/16/17/20, Phase 7).
2. Phases 4–5's remaining, non-invariant work (general notification-pipeline feature work, Mobile App scope beyond the reconciliation guarantee) — still core correctness, but not on the seat-reservation critical path.
3. The non-invariant remainder of Phase 6 (correlation-ID propagation, dashboards) and Phase 7 (K8s manifest work beyond the migration/self-healing/rate-limit guarantees; CI stage 5 packaging) and non-critical-path features (AI summarization, extra notification channels) — deferred without blocking the phases above.

**Guarantees:** a schedule slip shows up as a delayed non-invariant test deliverable, never as a skipped or weakened test for any Non-Negotiable Invariant, in any phase.
