# Test Plan — UniHub

This file is the phase-by-phase execution schedule for `test-strategy.md`, walking `proposal.md` §15's eight delivery phases through a testing lens: what test artifact each phase must produce, and what must be true before the next phase starts. It deliberately does **not** carry a sprint calendar or a staffing table — `proposal.md` §16 states this is a single-developer delivery, so a plan built around parallel testers or sprint velocity would describe a team that doesn't exist. Phase gates, not calendar dates, are the unit of progress here.

**Out of scope, and where it actually lives:** ratios, gates, environment tiers, and the Non-Negotiable Invariant catalog (INV-01…INV-18) that apply across every phase (`test-strategy.md`); per-level tooling detail (`../test-levels/*.md`); concrete load-test scenario mechanics (`../non-functional/performance-load.md`); resilience/fault-injection scenario mechanics — circuit breaker, Redis outage, replica lag, pod kill (`../non-functional/resilience-testing.md`); adversarial security-test mechanics — JWT tampering, QR forgery, rate-limit bypass (`../non-functional/security-testing.md`); Clock-injection/short-TTL mechanics for time-based tests (`../guidelines/mocking-guidelines.md`/`../guidelines/test-data-management.md`); the actual traceability rows (`../reports/test-matrix.md`); per-phase sign-off records once a phase is actually reached (`../reports/release-sign-offs/`).

## 1. Phase-by-Phase Test Plan

**Rationale:** `proposal.md` §15 already fixes what functionality lands in each phase. This section adds, per phase, the test deliverable that phase cannot be called done without, and the concrete exit check — so "the phase is finished" has the same evidentiary bar as `test-strategy.md` §1's objectives, not just "the feature runs on my machine."

**Model:**

| Phase (`proposal.md` §15) | Feature scope | Test deliverable this phase must produce | Exit criteria |
|---|---|---|---|
| **1 — Foundation** | Domain model, auth, Workshop module (create/list/detail), Web scaffolding | CI pipeline stood up as a Phase 1 deliverable — stages 1–3 (lint, unit+coverage, integration) from day one, stage 4 (contract diff vs. `packages/api-contract`) wired in as soon as the User/Workshop endpoints produce their first real OpenAPI output — not deferred to Phase 7 (see §2 below and `test-strategy.md` §4); unit tests for permission-evaluation logic (INV-01, User module), including an adversarial test with a tampered/escalated-permission JWT (`../non-functional/security-testing.md`); unit + integration tests for Workshop CRUD; integration test proving the nightly student-sync pipeline isolates malformed/duplicate records into an error store without halting the batch (INV-13 — phase assignment is an assumption: `proposal.md` §15 doesn't name a phase for nightly sync, and Phase 1 is chosen only because the User module that owns it is built here); first Web component/unit tests for the Phase 1 endpoints (tool not yet chosen, same open item as E2E) | RBAC integration test (INV-01) proves permission-based (not role-name) checks against a real JWT + real Postgres, and rejects a tampered JWT attempting privilege escalation; ≥80% coverage on User/Workshop core logic; CI blocks a merge on lint/unit/integration failure from Phase 1 onward, and on contract drift once the first OpenAPI output exists; nightly-sync test proves bad records land in the error store and the batch completes |
| **2 — Registration & Payment** | Registration flow (free/paid), payment gateway (sandbox) integration | Integration test for the idempotency-key write, same transaction as the business effect (INV-02) — landed here rather than `proposal.md` §15's Phase 3 grouping because the idempotency-key write has to exist the moment the first registration/payment request lands, not deferred to the concurrency-hardening phase (a deliberate reordering ahead of `proposal.md` §15's own grouping, not a scope change); integration test proving consistency-sensitive reads (idempotency lookup, immediate post-write view) are routed to the Master, never the Replica (INV-03); integration test proving the registration-confirmed outbox row commits in the same transaction as the registration write (INV-10, `architecture.md` §4.3, §6.1); integration test for the Pending, >15-minute payment-reconciliation cron calling the gateway status API and resolving the ticket (INV-04) — uses an injectable `Clock` and a config-shortened TTL rather than a real 15-minute wait (mechanics belong in `../guidelines/mocking-guidelines.md`/`../guidelines/test-data-management.md`); integration test proving the circuit breaker opens against a slow/dead payment-gateway sandbox while browsing and check-in keep working (INV-05, fault isolation — `../non-functional/resilience-testing.md`); unit tests for payment orchestration | Idempotency test proves a retried payment request produces zero duplicate charges; Master-routing test proves no stale-replica read can let a duplicate slip through; outbox test proves the event row and the business write commit or roll back together — never one without the other; reconciliation test proves a stuck Pending payment resolves to Successful/Cancelled without ever receiving a webhook; circuit-breaker test proves a payment-gateway outage never cascades into browsing/check-in |
| **3 — Concurrency Protection** | Seat-hold lifecycle, overbooking prevention, payment idempotency (`proposal.md` §11.1–11.2) | Testcontainers-based concurrent-access test, many threads competing for a small number of seats — the Phase 3 evidence gate for anti-overbooking (INV-06); a second variant of that test disables the Redis distributed-lock layer specifically, to prove the optimistic-lock version check plus the DB check constraint alone still hold 0% overbooking; a third test attacks the DB check constraint directly (bypassing the application layer, e.g. a raw concurrent `UPDATE`) to prove capacity can never go negative at the storage layer; integration test proving a Redis-coordination outage causes registration writes to be rejected rather than proceeding uncoordinated (INV-08, `architecture.md` §4.2, `../non-functional/resilience-testing.md`); integration test proving a seat left "Reserved" >15 minutes is released automatically without blocking the registration path (INV-07) — via injectable `Clock`/shortened TTL, not a real 15-minute wait — and doubling as the first proof that a scheduled job runs on exactly one instance at a time (INV-09, `architecture.md` §4.6); first authored draft of the 500-VU K6 adversarial script, run once locally as a smoke check only — it is **not** the evidence gate for this phase, the Testcontainers tests above are | Local (non-K8s) Testcontainers tests demonstrate 0% overbooking through each protection layer independently — full stack, lock-disabled, and DB-only (INV-06) — before this is trusted at full-topology load (Phase 8); Redis-outage test proves writes are rejected, never uncoordinated (INV-08); seat-hold release test proves automatic release with no blocked request (INV-07); one-instance test proves no duplicate job execution across parallel instances (INV-09) |
| **4 — Notifications** | Async, extensible notification pipeline | Integration test simulating RabbitMQ redelivery, proving every consumer is idempotent under redelivery (INV-11); end-to-end outbox-relay test proving a committed outbox row (Phase 2, INV-10) is actually published and consumed, not silently stranded | Redelivery test (INV-11) proves reprocessing is a safe no-op — no duplicate notification side-effect; outbox-relay test (INV-10) proves no committed event is left unpublished |
| **5 — Offline Check-in** | Digital ticket issuance, offline scanning, check-in reconciliation, Mobile App build | On-device signature-verification test (JOSE, mobile test runner — tool not yet chosen) proving INV-12's offline self-verification, including a forged/tampered-QR rejection case and a valid-signature-but-cancelled-workshop case that must still be rejected at server-side reconciliation (`../non-functional/security-testing.md`); durable-queue test (Expo SQLite/Drizzle survives simulated restart); server-side reconciliation test with duplicate scans from multiple simulated devices (INV-12); first Check-in Client unit/component tests beyond the signature/queue tests above (tool not yet chosen, same open item as the Web tests in Phase 1) | Reconciliation test proves earliest-timestamp-wins holds regardless of device/arrival order (INV-12); forged-QR and cancelled-but-signed-ticket cases are both rejected, never checked in |
| **6 — Observability** | Metrics, dashboards, tracing | Test asserting Correlation ID propagates end-to-end (HTTP → RabbitMQ → log); test simulating an audit-pipeline outage during a registration/payment/check-in operation (INV-14, `architecture.md` §5.5) | Propagation test passes across at least one async hop; audit-outage test (INV-14) proves the business operation still succeeds and the audit-publish failure surfaces as an operational alert, never a silent drop |
| **7 — Kubernetes Deployment** | Full K8s manifests, CI/CD | CI stage 5 (Docker package/push) wired as the pipeline's final step — stages 1–4 are already live since Phase 1 (see that row and `test-strategy.md` §4); smoke test against the deployed full topology; migration compatibility check proving an old pod version can still read the schema during a rolling update (INV-15, `architecture.md` §6.2); kill-pod test proving an unhealthy instance is restarted automatically and traffic only reaches ready instances (INV-16); rate-limit test proving the limiter is enforced off shared state across ≥2 parallel instances, not bypassable per-instance (INV-17, `../non-functional/security-testing.md`) | Full CI pipeline (stages 1–5) passes end to end on a merge; smoke test passes on a fresh Minikube deploy; migration test proves the old pod version does not break against the post-migration schema mid-rollout (INV-15); kill-pod test proves automatic recovery (INV-16); rate-limit test proves no per-instance bypass (INV-17) |
| **8 — Performance & Concurrency Testing** | Load testing against the documented surge and adversarial scenarios | Full 12,000-CCU K6 run, asserting sub-second p95 on seat-reservation/registration-confirmation endpoints (Peak Load Capacity + Registration Latency, `proposal.md` §12); 500-VU adversarial rerun at full topology (not just local, per Phase 3) | Every row of `proposal.md` §12's success-criteria table has evidence, including the two latency/capacity rows added in `test-strategy.md` §1; results recorded via `../reports/test-matrix.md` and a phase sign-off (`../reports/release-sign-offs/`) |

**Guarantees:** no phase is marked complete on functionality alone — each row's exit criterion must be met before the next phase's work begins, mirroring `proposal.md` §15's own framing that each phase builds on a *working* system rather than deferring integration to the end.

## 2. Prioritization Under Single-Developer Bandwidth

**Rationale:** `proposal.md` §16 names single-developer bandwidth as a schedule risk and already sets the mitigation: registration, payment, and concurrency correctness are the critical path; AI summarization and additional notification channels are scope delivered only after core correctness is proven. Test-writing effort follows the same order — there is no separate "testing team" to parallelize against a different priority.

**Model:** if a phase's test deliverable and a lower-priority feature's test deliverable compete for the same time, the order is:

1. The CI gate itself (stages 1–4, stood up in Phase 1 — see §1) never slips, because it's the enforcement mechanism for everything below it. Same rule for anything touching a catalogued invariant (`test-strategy.md` §2), regardless of which phase it lands in: RBAC + nightly-sync isolation (INV-01, INV-13, Phase 1); idempotency-key write, Master-routing, outbox-atomicity, payment reconciliation, circuit breaker (INV-02/03/04/05/10, Phase 2); anti-overbooking, seat-hold release, Redis fail-safe, one-instance-per-job (INV-06/07/08/09, Phase 3); consumer redelivery-idempotency, outbox-relay (INV-10/11, Phase 4); earliest-timestamp-wins reconciliation, QR/cancelled-workshop rejection (INV-12, Phase 5); audit-fail-open (INV-14, Phase 6); migration mid-rollout compatibility, self-healing, rate-limit (INV-15/16/17, Phase 7).
2. Phases 4–5's remaining, non-invariant work (general notification-pipeline feature work, Mobile App scope beyond the reconciliation guarantee) — still core correctness, but not on the seat-reservation critical path.
3. The non-invariant remainder of Phase 6 (correlation-ID propagation, dashboards) and Phase 7 (K8s manifest work beyond the migration/self-healing/rate-limit guarantees; CI stage 5 packaging) and non-critical-path features (AI summarization, extra notification channels) — deferred without blocking the phases above.

**Guarantees:** a schedule slip shows up as a delayed non-invariant test deliverable, never as a skipped or weakened test for any Non-Negotiable Invariant, in any phase.
