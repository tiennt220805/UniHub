# Web (Frontend) Coding Standards — UniHub Guidelines

*Status: Draft — áp dụng từ Mục 1 (Walking Skeleton). Sẽ rà soát và mở rộng khi có thêm code
thật, theo đúng cách `backend-coding-standards.md` đã hình thành (xem cơ chế Open Items ở §27
file đó làm mẫu).*

This is the frontend counterpart to `backend-coding-standards.md`, covering `apps/web`. It
records four decisions made ahead of Mục 1 — nothing here goes beyond them.

---

## 1. Directory Structure

**Decision.** Type-first, then domain inside each type: `components/<domain>/`,
`pages/dashboard/{admin,organizer,student}/`, `hooks/<domain>/` (only once a hook is actually
extracted per §3 — `hooks/` is not a standing directory), and so on. Role folder names follow
UniHub's own domain vocabulary — `organizer`/`student` — and `pages/public/` holds the Student
browse/view flow that needs no login.

**Why.** A type-first layout keeps each React concern (components, pages, hooks, store) in one
place while still grouping by domain inside it, so a change to one module's UI stays inside one
subtree per type instead of scattering across an unrelated folder-per-feature split. Role names
come from UniHub's ubiquitous language — same principle `backend-coding-standards.md` §14.2
applies to the backend (names are cited from the source of truth, never invented). There is no
separate `utils/` next to `lib/`: `apps/web/src/lib/utils.ts` already exists from the Mục 0
Shadcn scaffold (the `cn()` helper), and a second general-helpers directory would just split the
same kind of code across two places with no rule for which one a given helper belongs in.

**Example.**

```
src/
  assets/
  components/
    ui/                    # Shadcn primitives
    workshop/
    registration/
  pages/
    auth/
    public/                # Student browses/views workshops, no login required
    dashboard/
      admin/
      organizer/
      student/
  layouts/
  routes/
  store/                   # Zustand, one file per domain
  types/
    schema.gen.ts          # generated by openapi-typescript, not committed — see §2
  lib/
  hooks/                   # appears only once a useQuery/useMutation is extracted for reuse in ≥2 places — see §3
```

## 2. API Types

**Decision.** Generate TypeScript types with `openapi-typescript` from
`packages/api-contract/openapi.yaml` — types only, no request/fetch functions generated. The
generated file is not committed; it is regenerated automatically before `dev`/`build`, playing
the same role for the frontend that `bundleApiContract` plays for the backend.

**Why.** `packages/api-contract` is already the declared source of truth for the HTTP shape
(per `CLAUDE.md`); generating types from it keeps the frontend from drifting out of sync with
the contract without pulling in a full generated client this early.

**Example.**

```json
// apps/web/package.json
{
  "scripts": {
    "predev": "openapi-typescript ../../packages/api-contract/openapi.yaml -o src/types/schema.gen.ts",
    "prebuild": "openapi-typescript ../../packages/api-contract/openapi.yaml -o src/types/schema.gen.ts",
    "dev": "vite",
    "build": "tsc -b && vite build"
  }
}
```

```gitignore
# apps/web/.gitignore
src/types/schema.gen.ts
```

## 3. TanStack Query

**Decision.** Call `useQuery`/`useMutation` directly inside the page/component that needs them,
with the query key written inline as a literal array. Extract to a dedicated hook file only
once the same call is reused in 2 or more places — at that point the query key factory moves
into the same file as the extracted hook (e.g. `hooks/workshop/queries.ts`), not a separate
`lib/query-keys/` directory. Hook names follow `use<Noun>` / `use<Verb><Noun>`; wherever a query
key factory lives, it is shaped `{ all, lists, list(filters), detail(id) }`.

**Why.** Avoids a premature abstraction layer over a data-fetching call used exactly once.
Co-locating the key factory with the hook that owns it, instead of a standalone
`lib/query-keys/` directory, keeps one query's definition in one file rather than split across
two directories for no benefit until a second consumer actually shows up.

**Example.**

```ts
// pages/workshop/WorkshopDetailPage.tsx — used once: key written inline, no factory yet
const { data } = useQuery({
  queryKey: ['workshops', 'detail', workshopId],
  queryFn: () => getWorkshop(workshopId),
});
```

```ts
// hooks/workshop/queries.ts — extracted once WorkshopDetailPage and WorkshopCard both need it;
// the key factory lives here, next to the hook, not in a separate lib/query-keys/ directory
export const workshopKeys = {
  all: ['workshops'] as const,
  lists: () => [...workshopKeys.all, 'list'] as const,
  list: (filters: WorkshopFilters) => [...workshopKeys.lists(), filters] as const,
  detail: (id: string) => [...workshopKeys.all, 'detail', id] as const,
};

export function useWorkshop(workshopId: string) {
  return useQuery({
    queryKey: workshopKeys.detail(workshopId),
    queryFn: () => getWorkshop(workshopId),
  });
}

export function useRegisterForWorkshop() {
  return useMutation({ mutationFn: registerForWorkshop });
}
```

## 4. Zod Schemas

**Decision.** Form validation schemas are hand-written and kept separate from the types
generated from the contract (§2). Where a form's shape differs from its request's shape, an
explicit mapping function converts between them.

**Why.** Contract-generated types describe the wire shape the backend expects, not necessarily
the shape that makes for good form UX; collapsing the two would leak the request representation
into forms and break form code on unrelated contract changes.

**Example.**

```ts
// components/registration/registration-form.schema.ts
const registrationFormSchema = z.object({
  fullName: z.string().min(1),
  studentId: z.string().regex(/^\d{8}$/),
  dietaryNote: z.string().optional(),
});

type RegistrationFormValues = z.infer<typeof registrationFormSchema>;

// explicit map — form shape != CreateRegistrationRequest shape
function toCreateRegistrationRequest(
  values: RegistrationFormValues,
  workshopId: string,
): components['schemas']['CreateRegistrationRequest'] {
  return {
    workshopId,
    studentId: values.studentId,
    fullName: values.fullName,
    note: values.dietaryNote ?? null,
  };
}
```
